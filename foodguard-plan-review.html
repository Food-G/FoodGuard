FoodGuard 계획 대비 점검

세부 과제 계획서의 목표를 기준으로 현재 코드를 전부 읽고 평가했습니다. 같은 일을 하는 국내외 서비스와 연구의 예측 모델, 기능, 성과도 나란히 비교했습니다.

기준 코드: jhy 브랜치 (dev 2de3d30과 코드 동일)검토 범위: AI 서비스 약 1,400줄 · 백엔드 약 3,000줄 · 프론트엔드 약 8,200줄작성: 2026-10-16연구 방향 문서
한눈에
  1. 계획서의 기능 범위는 대부분 만들어져 있습니다. 7일 수요 예측, 발주 추천과 자동 발주, 본사 승인부터 배송·QR 검수·재고 반영까지 이어지는 발주 흐름, 폐기 예측, 기부 기록이 있습니다.
  2. 계획서의 정량 목표 세 가지는 지금 구조로는 측정할 수 없습니다. 지난 예측이 덮어써져 남지 않고, 실제 폐기를 기록하는 곳이 없고, 점주가 추천을 고쳤는지 남지 않습니다.
  3. 유사 서비스와 비교하면 차별점이 분명합니다. 본사-가맹점-배송 검수를 하나로 묶은 흐름과, 폐기 예측에서 기부로 이어지는 연결은 비교한 서비스들에서 찾지 못했습니다. 약점은 효과 측정과 보안입니다.
  4. 보안 문제가 현장 적용의 가장 큰 걸림돌입니다. 공개 저장소에 DB 비밀번호, JWT 서명 키, 기상청 API 키가 들어 있고, 서버는 역할이나 매장 소유를 확인하지 않습니다.
  5. 본사 통계 화면의 수치는 하드코딩된 가상 값입니다. "폐기율 12.5% 감소" 같은 문구가 실측처럼 보이므로, 발표에서는 예시 화면이라고 밝히거나 실제 데이터로 바꿔야 합니다.

주간 ±10% 이내		 화면의 "신뢰도"는 100 − wMAPE입니다. 이 값은 시간 순서를 무시한 교차검증으로 학습 구간 안에서 계산됩니다(demand_predictor.py:150). 재예측하면 미래 예측을 지우고 다시 쓰므로(data_service.py:77) 지난 예측과 실제 판매를 비교할 수 없습니다. 15~20% 절감		 폐기 "예측"만 있습니다(WastePredictionService). 실제 폐기량을 저장하는 필드가 없습니다. 초기 설계(schema.sql)에는 waste_quantity가 있었지만 실제 엔티티(Inventory.java)에서는 빠졌습니다. 식자재 원가도 없어서 폐기 금액도 계산할 수 없습니다. 12개국 식당 114곳 첫해 주방 폐기 26% 감소 [4]. 식료품점 AI 발주 도입 사례 매장당 14.8% [5]. 발주량 추천
점주 80% 이상 활용		 추천 미리보기 API(/orders/recommend)는 있지만 이를 쓰는 화면이 없습니다. 점주는 "자동 발주" 버튼으로 추천을 그대로 발주 요청으로 만듭니다(Orders.tsx:133). 추천을 수정하거나 거절한 기록이 남지 않습니다. 육수당 88개 매장 AI 발주 사용률 81.1%, 추천 수량 그대로 발주 60% 이상 [2]. 80%는 국내 사례와 비교해 현실적인 목표입니다. "사용률"과 "그대로 승인한 비율"을 나눠 정의하고, 승인·수정·거절을 기록해야 측정할 수 있습니다. 측정 설계 필요

적용 가능성		 단위를 kg·L·개로 제한하고 레시피 단위를 자동으로 맞춥니다. 발주는 3단계 QR 검수와 배송 위치 공유까지 갖췄습니다. 반면 판매 기록에 시각이 없어(SalesData는 날짜만) 시간대 예측이나 품절 추정을 할 수 없습니다. 보안 문제는 아래 경고를 참고하세요. OWASP Top 10(2021)에서 접근 통제 실패가 1위 위험입니다 [10]. 보안 문제를 고치기 전에는 실제 가맹점 데이터로 시범 운영을 할 수 없습니다. 고친 뒤에는 발주 흐름의 완성도가 강점이 됩니다. 보안 해결 전 불가

현장 적용 전에 반드시 고칠 보안 문제

  • 비밀 정보 노출: backend/src/main/resources/application.properties에 TiDB 접속 주소, 실제 DB 비밀번호, JWT 서명 키가 들어 있고, ai-service/.env.example에 기상청 API 키가 들어 있습니다. GitHub 저장소는 로그인 없이 받을 수 있는 공개 상태입니다. 세 값 모두 재발급하고 환경변수로 옮겨야 합니다. 새 값으로 바꾸면 이력에 남은 옛 값은 쓸모가 없어집니다.
  • 역할 검사 없음: JWT 필터가 권한을 비운 채 인증만 처리합니다(JwtFilter.java). 로그인한 점주라면 누구나 본사 전용 API(전체 발주 조회, 발주 승인)를 호출하거나 다른 매장의 데이터를 볼 수 있습니다.
  • 본사 관리자 자유 가입: 회원가입 화면에서 "본사 관리자"를 고를 수 있고 서버도 그대로 받아들입니다(UserService.signup).
  • 검수 우회 가능성: 배송 기사용 그룹 링크가 각 품목의 QR 토큰을 내려주고, 점주 검수 API는 토큰만 있으면 인증 없이 동작합니다. 링크를 가진 사람이 점주 검수까지 끝낼 수 있습니다.
2 · 예측모델 예시

FoodGuard 모델은 실제로 이렇게 동작한다

코드를 그대로 따라가며, 메뉴 하나의 예측이 식자재 발주량이 되기까지를 단계별로 정리했습니다. 수치는 동작을 보여주기 위한 가상의 예시입니다.

① 데이터 양 판단판매 이력이 몇 일치인지에 따라 모델을 고릅니다. 30일 이상이면 XGBoost에 피처 16개와 날씨 6개를 씁니다.예: 김치찌개 45일치 → 전체 피처
② 학습점예측 모델과 60% 분위수 모델을 같은 데이터로 따로 학습합니다. 60%는 원가 비율 0.4에서 나온 뉴스벤더 기준입니다.재예측할 때마다 다시 학습
③ 7일 예측날마다 점예측과 추천량을 냅니다. 추천량은 둘 중 큰 값입니다.예: 점예측 38 · 분위수 41 → 추천 41그릇
④ 식자재 환산7일 추천량을 모두 더한 뒤 레시피로 식자재 양을 구하고, g은 kg으로, ml은 L로 바꿉니다.예: 321그릇 × 돼지고기 120g = 38.5kg
⑤ 발주량필요량에서 현재고와 아직 도착하지 않은 발주량을 뺍니다.예: 38.5 − 12.0 − 5.0 = 21.5kg

비교에서 보이는 FoodGuard의 자리

  • 강점: 예측 → 발주 추천 → 본사 승인 → 발송 → 기사 수령 → 점주 검수 → 재고 반영까지 한 시스템에서 이어집니다. 비교한 서비스들은 대부분 예측·발주 추천이나 폐기 측정 중 한쪽에 집중합니다. 폐기 예측에서 기부 기록으로 이어지는 연결도 다른 서비스에서는 확인하지 못했습니다.
  • 약점: 다른 서비스가 최소한 사용률이나 정확도를 공개하는 데 비해 FoodGuard는 아직 측정 수단이 없습니다. 점주 피드백을 받는 구조(Afresh, 한큐)도 없습니다.
  • 기회: 비교한 서비스 중 독립적으로 검증된 폐기 감축 수치를 공개한 곳은 거의 없었습니다. FoodGuard가 백테스트와 시뮬레이션으로 폐기·품절 효과를 측정해 공개하면, 학생 프로젝트로서 가장 확실한 차별점이 됩니다.

우선순위

순서할 일이유
1DB 비밀번호·JWT 키·기상청 키 재발급, 환경변수로 이동. 서버에 역할·매장 소유 검사 추가, 본사 관리자 가입 막기공개 저장소라 지금도 누구나 DB에 접속할 수 있습니다.
2예측 기록, 실제 폐기 입력, 추천 승인·수정·거절 기록 추가계획서 정량 목표 세 가지를 재려면 이 기록이 필요합니다.
3본사 통계 화면을 실제 데이터로 바꾸거나 "예시 화면" 표시. 누락된 매출 요약 API 3개 구현가상 수치가 실측처럼 발표되면 신뢰를 잃습니다.
4발주 추천 미리보기 화면을 만들어 근거와 함께 보여주고, 승인 후 발주추천 활용률을 측정하고 의사결정 지원을 보여줄 수 있습니다.
5발주량 계산을 식자재별 보호기간 합계에 분위수 1회 적용으로 변경지금 방식은 7일치 안전재고를 쌓아 과잉 발주로 기웁니다.
6CLAUDE.md, uml, schema.sql, main.py 설명 갱신. 더미 데이터 생성기를 저장소에 추가보고서와 코드가 서로 다르면 심사에서 지적받기 쉽습니다.
한계

코드는 읽어서 분석했고 직접 실행하지는 않았습니다. 본사 대시보드 목록이 비는 문제는 코드 흐름으로 추정한 것입니다. 유사 서비스의 기능과 성과는 공개 기사와 업체 자료 기준이며, 대부분 독립적으로 검증되지 않았습니다. 기대평가의 외부 비교치는 대상과 단위가 FoodGuard와 달라서, 같은 조건의 비교가 아닌 참고 범위로 봐야 합니다.
