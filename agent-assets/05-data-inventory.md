# 05. 데이터 자산 인벤토리

> 에이전트가 학습·추론·RAG에 쓸 수 있는 데이터가 실제로 무엇이 있고, 어디까지 믿을 수 있는지.

## 1. 운영 데이터 (TiDB Cloud)

| 테이블 | 성격 | 에이전트 활용도 |
|---|---|---|
| `SALES_DATA` | 일별 매장×메뉴 판매수량 | ★★★ 수요·매출·이상탐지의 기반 |
| `PREDICTION_RESULT` | 7일 예측 (오늘 이후만 유지) | ★★★ 발주·폐기 의사결정 입력 |
| `MENU` / `MENU_INGREDIENT` | 메뉴 마스터 + 레시피(BOM) | ★★★ 수요 → 식자재 전개의 유일한 경로 |
| `INVENTORY` | 매장×식자재 현재고 | ★★☆ 스냅샷만, **이력 없음** |
| `ORDER_REQUEST` | 발주 이력 + 상태 + 시각 | ★★☆ 리드타임 분석 가능 (`ordered_at` ↔ `approved_at`) |
| `INGREDIENT` | 식자재 마스터 | ★★☆ |
| `STORE` / `USER` | 매장·계정 | ★☆☆ `region`이 날씨 조인키 |
| `NOTIFICATION` | 알림 | ★☆☆ 2026-09-11 쓰기 버그 수정됨 |

## 2. 확인된 데이터 규모 (`ai-service/*_check.txt` 스냅샷 기준)

- **판매 이력**: 메뉴 5종 × 60일 (2026-03-15 ~ 2026-05-13) — 메뉴당 정확히 60행.
  → 전부 `generate_dummy_data.py`로 만든 **합성 데이터**입니다.
- **식자재 마스터**: 26종 (한식 계열 `60001~60020`, 버거 계열 `90001~90006`).
- **학습된 모델**: 11개, 전부 `store_60005` (`menu_120001`, `menu_150001~150010`).
  → 실제 학습이 수행된 매장은 **1곳**.

## 3. 합성 데이터의 생성 규칙 (= 모델이 실제로 학습한 패턴)

`generate_dummy_data.py`:
```
요일 배율 = [월0.8, 화0.85, 수0.9, 목1.0, 금1.2, 토1.4, 일1.3]
기본 수량 = randint(10, 30)   # 메뉴별 고정
일별 수량 = round(기본 × 요일배율 × uniform(0.9, 1.1))
```

**이것이 의미하는 바 (중요)**:
- 데이터에는 **요일 효과 + ±10% 노이즈밖에 없습니다**. 추세·계절성·날씨 반응·프로모션 효과가 **존재하지 않습니다**.
- 따라서 현재의 높아 보이는 R²/confidence는 **"요일 평균을 잘 맞춘다"는 뜻**이지 모델 성능의 증거가 아닙니다.
- 날씨 피처는 학습에 들어가지만 **타깃과 상관이 0**입니다. 날씨 기여도를 주장하려면 실데이터가 필요합니다.
- → **에이전트 데모/평가는 이 한계를 명시하고 하세요.** 성능 주장을 하려면 실매장 데이터 확보가 선행 과제입니다.

## 4. 데이터 품질 이슈

| # | 이슈 | 영향 |
|---|---|---|
| 1 | ~~식자재 단위 규칙이 두 갈래~~ **해결 (2026-10-16)** — DB 감사 결과 식자재·재고는 전부 `kg/L/개`, 레시피는 `g→kg`·`ml→L`·`개→개` 조합만 존재. 이제 `UnitConverter`가 저장 시점(식자재 등록·수정, 레시피 등록)과 변환 시점 모두 비호환 조합을 거부(400)하고, 재고·레시피가 있는 식자재의 단위 변경도 막음 | 재발 방지됨. `update_ingredient_units.py`는 수량 환산 없이 단위 이름만 바꾸므로 **다시 실행 금지** |
| 2 | 식자재 이름 중복 (`60012 양파(개)`, `90004 양파(kg)`) | 이름 기준 매칭 불가, 반드시 ID 사용 |
| 3 | `MENU.price` 변경이 과거 매출에 소급 적용 | 시계열 매출 분석 왜곡 (`04-business-rules.md` §7) |
| 4 | `PREDICTION_RESULT`는 재예측 시 미래분을 DELETE | **예측 vs 실제 대조 이력 없음** → 정확도 측정 불가 |
| 5 | `INVENTORY`는 현재값만, 변동 이력 테이블 없음 | 폐기량·회전율 산출 불가 |
| 6 | 판매 시각 정보 없음 (날짜 단위) | 피크타임·시간대 예측 불가 |
| 7 | 폐기(waste)·기부(donation) 데이터가 **아예 없음** | 프론트에 화면은 있으나 저장소 없음 (`02-api-catalog.md` §4) |

## 5. 에이전트를 위해 새로 만들어야 할 데이터 자산

| 자산 | 왜 필요한가 | 최소 형태 |
|---|---|---|
| `PREDICTION_LOG` (예측 이력 보존) | 정확도(MAPE) 측정 → 에이전트가 "얼마나 믿을지" 판단 | 기존 DELETE를 archive로 바꾸거나 append-only 테이블 추가 |
| `INVENTORY_TXN` (재고 변동 원장) | 소모/입고/폐기 구분, 회전율·폐기율 | `(store, ingredient, delta, reason, ts)` |
| `WASTE_RECORD` | 폐기 예측 에이전트의 정답 레이블 | `(store, ingredient, qty, reason, date)` |
| 실매장 판매 데이터 | 합성 데이터의 한계(§3) 해소 | 최소 90일 |
| 이벤트/프로모션 캘린더 | 이상치 설명 피처 | `(store, date, type, note)` |
