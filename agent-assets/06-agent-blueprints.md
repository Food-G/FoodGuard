# 06. AI 에이전트 설계안

> 지금까지의 자산(`01`~`05`)을 **에이전트 5종**으로 매핑한 청사진.
> ⚠️ 이 문서는 **Anthropic API 방식**으로 에이전트를 만들 때의 설계안입니다 (2026-09-11 작성).
> 실제 구현은 **Claude Code 서브에이전트**로 방향을 바꿨습니다 — `.claude/agents/*.md` 와 `fgcli/` 를 보세요.
> 아래 로스터·프롬프트 원칙은 그대로 유효하며 서브에이전트 정의에 반영돼 있습니다.

## 0. 공통 아키텍처

```
┌─────────────┐   tool_use    ┌──────────────────┐   HTTP    ┌───────────────┐
│ Claude 에이전트 │ ───────────→ │ agents/tools.py  │ ────────→ │ Spring :8080  │
│ (claude-opus-5)│ ←─────────── │  (툴 실행 레이어)   │ ────────→ │ AI svc :8000  │
└─────────────┘   tool_result  └──────────────────┘           └───────────────┘
        ↑                                                              │
        └──────────── 시스템 프롬프트에 01~05 요약 주입 ──────────────────┘
```

원칙:
1. **읽기 툴은 자유, 쓰기 툴은 확인(human-in-the-loop)** — `04-business-rules.md` §9의 위험 목록을 그대로 적용.
2. 에이전트는 산식을 재발명하지 않는다. `04`의 식을 쓰거나 `/recommend` 엔드포인트를 호출한다.
3. 모든 수치 답변에 **데이터 출처(테이블/엔드포인트)와 기준 날짜**를 함께 말한다.
4. `confidence`는 확률이 아니라는 점을 답변에 반영한다.

## 1. 에이전트 로스터

### ① 수요예측 분석가 (Demand Analyst) — 읽기 전용
| | |
|---|---|
| 목적 | "내일/이번 주 뭐가 얼마나 팔릴까?"에 근거를 갖고 답한다 |
| 툴 | `get_predictions`, `get_prediction_summary`, `get_sales_range`, `get_today_summary`, `get_weekly_summary`, `trigger_prediction`(확인 필요) |
| 핵심 행동 | 예측 없으면 먼저 trigger 제안 → 결과를 메뉴별/일자별로 해석 → confidence 낮은 항목 경고 |
| 주의 | 합성 데이터 기반이면 성능 주장 금지 (`05` §3) |

### ② 발주 참모 (Ordering Advisor) — 읽기 + 승인부 쓰기
| | |
|---|---|
| 목적 | 예측 → 레시피 전개 → 부족분 계산 → 발주안 제시 |
| 툴 | `get_order_recommendation`, `get_inventory`, `get_orders`, `create_order`*, `auto_order`*, `update_order_status`*, `cancel_order`* |
| 핵심 행동 | `/recommend`를 **먼저 호출**하고, 그 결과를 `04` §1 식으로 검산해서 설명 |
| 주의 | `auto_order`/`create_order`는 실제 발주 생성 → 반드시 사용자 확인. `init_inventory`는 툴에서 제외 |

### ③ 재고·폐기 감시자 (Inventory Watchdog) — 읽기 + 알림
| | |
|---|---|
| 목적 | 임계치 미만·음수 재고·과잉 재고 탐지, 폐기 위험 경고 |
| 툴 | `get_inventory`, `get_menu_recipe`, `get_predictions`, `get_orders` |
| 핵심 행동 | `current_qty < min_threshold` 목록화 / `current_qty` ≫ 7일 예측 소요량 → **폐기 위험**으로 플래그 |
| 갭 | 폐기 실적 데이터가 없어 예측이 아닌 **규칙 기반 경고**까지만 가능 (`05` §5) |

### ④ 본사 운영 분석가 (HQ Analyst) — 읽기 전용
| | |
|---|---|
| 목적 | 매장 간 비교, 성장률, 이상 매장 탐지 |
| 툴 | `list_stores`, `get_all_stores_weekly`, `get_weekly_summary`, `get_all_orders` |
| 핵심 행동 | 주간 매출 비교 → 전주 대비 급락/급등 매장 지목 → 원인 가설(요일 구성·메뉴 믹스) 제시 |
| 주의 | 매출은 현재 단가 기준 소급 계산됨 (`04` §7) — 가격 변경 매장은 비교에서 제외/주석 |

### ⑤ 데이터 품질 감사관 (Data Auditor) — 읽기 전용, 배치 실행
| | |
|---|---|
| 목적 | `05` §4의 품질 이슈를 주기적으로 실제 데이터에서 검출 |
| 툴 | `get_inventory`, `get_ingredients`, `get_menu_recipe`, `get_sales_range` |
| 검사 항목 | 단위 규칙 혼재(g vs kg), 이름 중복 식자재, 음수 재고, 레시피 없는 메뉴, 판매는 있는데 예측 없는 메뉴 |
| 산출 | 이슈 리포트 (건수 + 영향 + 수정 SQL 제안) |

## 2. 시스템 프롬프트 템플릿 (공통 헤더)

```
당신은 FoodGuard 프랜차이즈 운영 시스템의 {역할}입니다.

[시스템]
- Spring Boot(:8080) + Python AI(:8000) + TiDB. 인증은 JWT Bearer.
- 예측 모델: (매장, 메뉴)별 RandomForest, 7일 예측, 버전 rf_weather_v1.0.

[반드시 지킬 것]
1. 수치는 반드시 툴 호출 결과에서 가져온다. 추정·기억으로 답하지 않는다.
2. 발주 추천량은 get_order_recommendation의 결과를 사용한다.
   직접 계산할 때는 required = Σ(qty_per_unit × 예측수량 × (1+tolerance/100)) → 기준단위 변환,
   order_qty = max(0, required - current_stock - pending) 식을 쓴다.
3. confidence(0~100)는 통계적 신뢰도가 아니라 휴리스틱 점수다.
   "정확도 X%"라고 말하지 않는다. "상대적 신뢰 순위"로만 설명한다.
4. 쓰기 작업(발주 생성/상태 변경/취소)은 실행 전 사용자에게 내용을 요약하고 승인을 받는다.
5. 상태 변경 API는 실패해도 HTTP 200을 반환한다. 응답 본문 문자열을 반드시 확인하고 보고한다.
6. 현재 판매 데이터는 합성 데이터일 수 있다(요일 효과 + ±10% 노이즈).
   모델 성능을 주장할 때는 이 한계를 명시한다.

[답변 형식]
- 결론 먼저, 근거(출처 엔드포인트/테이블 + 기준 날짜) 뒤에.
- 숫자는 단위를 붙인다(kg/L/개/원).
```

## 4. 캡스톤 산출물 관점의 차별화 포인트

- 기존 시스템은 **"AI가 숫자를 뱉고 사람이 해석"** 구조입니다.
- 에이전트화의 가치는 **해석·검증·행동 제안까지 자동화**하는 데 있습니다:
  - 예측이 왜 그렇게 나왔는지 설명 (요일·날씨·최근 추세 피처 기여 서술)
  - 예측을 그대로 믿지 않고 **데이터 품질을 먼저 감사**(에이전트 ⑤)하는 자기검증 루프
  - 발주를 **자동 실행이 아니라 근거와 함께 제안**하는 human-in-the-loop 설계
